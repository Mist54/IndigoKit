# Accessibility

IndigoKit is developed toward **WCAG 2.2 AA**. This document records the conventions and measured evidence. **IndigoKit does not claim formal compliance or certification** — accessibility is a property of the complete application, not a stylesheet.

## Semantic HTML

- Use real elements: `<button>` for actions, `<a href>` for navigation, `<ul>/<ol>` for lists, `<table>` with `<thead>/<tbody>/<th scope="col|row">` for tabular data, `<fieldset>/<legend>` for grouped form controls.
- Headings must form a logical outline (no skipped levels in page flow). Popup contexts (modal titles, dropdown headers) may use their own heading levels.
- Landmarks: `<nav>`, `<main>`, `<header>`, `<footer>` — navigation regions should have an accessible name where context requires it (e.g. `aria-label="Breadcrumb"`).
- Do not turn tables into div grids or lists into clickable divs. No unnecessary ARIA — native semantics first.

## Labels and accessible names

- Every form control needs a label: `<label for>`, `aria-labelledby`, or `aria-label`. Help text via `aria-describedby` or `.form-text`.
- Icon-only buttons must have an accessible name (`aria-label`). A tooltip is **not** an accessible name.
- Required fields: `required` + visible marker + `.form-text` guidance. Validation errors: `.invalid-feedback` text + icon + border — never color alone.
- Close buttons (`btn-close`) carry `aria-label="Close"`.

## Icons

- Decorative icons: `aria-hidden="true"`.
- Meaningful icons must never be the only source of information — pair them with text or an accessible name.
- Icon-only controls stay keyboard-focusable real buttons/links.

## Keyboard

- All interactive controls are reachable in native Tab order — no traps.
- Bootstrap provides modal/offcanvas focus containment, Escape dismissal, and focus return; the IndigoKit shell drawer does the same (Tab wrap, Escape, focus restore, `inert` on background content).
- Accordion buttons, carousel controls, pagination, tabs, and dropdowns use native button semantics — Enter/Space work without custom code.
- Visible focus is required on every interactive element (see Focus).

## Focus

- Global focus: the theme-aware ring (`--bs-focus-ring-color`) plus a `:focus-visible` solid outline — **never** `outline: none`.
- Light: solid indigo ring ≈6.3:1. Dark: indigo-300 (`#A5B4FC`) — outline ≈9:1 on body, ring ≈5.7:1. Both ≥ the 3:1 focus-appearance bar.
- Validated form controls use the same strong ring (not the raw semantic colors, which measured below 3:1 in light).
- Nothing in IndigoKit removes or weakens focus indicators.

## Contrast

Measured (computed, both themes) — see [Theming](theming.md#contrast-across-themes) for the table. Every active text pair is ≥4.5:1 and every focus indicator ≥3:1. Exceptions are documented there (placeholder/disabled text, which WCAG exempts).

## Color dependence

No UI state is communicated by color alone. Every state carries a second cue:

- Badges: text + color. Alerts: heading/text + color.
- Validation: icon + border + message text.
- Tables: contextual text ("Healthy" / "Down") + tint.
- Active navigation: shape/weight + `aria-current="page"` / `aria-selected` / `aria-pressed` + color.
- Progress: percentage label + bar.

## Component-specific conventions

- **Tables:** `<caption>` where useful, `th scope`, header emphasis — never rely on tint alone for meaning.
- **Toasts:** dynamic notifications — `role="status"` for non-urgent info, `role="alert"` only for genuinely urgent/error messages. Dismissible toasts keep a real keyboard-accessible close button. Toasts complement, never replace, persistent alerts.
- **Modals / offcanvas:** accessible name (`.modal-title` / `.offcanvas-title`), focus moved into the dialog, contained while open, Escape to close, focus returned on close.
- **Tooltips/popovers:** triggers keep an accessible name independent of the tooltip; hover-only information must also be reachable by keyboard (focus). Do not put essential instructions only in a tooltip.
- **Accordion:** real headings + `.accordion-button` (native button, `aria-expanded`/`aria-controls` generated by Bootstrap).
- **Carousel:** controls and indicators are real buttons with accessible names; meaningful images have `alt`; decorative images are `aria-hidden`/empty `alt`. **No autoplay by default** in IndigoKit demos.
- **Scrollspy / navigation:** active state is not color-only; current page marked with `aria-current`.
- **Progress:** `role="progressbar"` with `aria-valuenow/min/max`; percentage visible as text where it matters.
- **Loading:** a spinner alone is not an accessible message — pair it with visually hidden or visible text ("Loading…"). Buttons in a loading state keep their text ("Saving…") and disable appropriately.

## Reduced motion

- All transitions come from Bootstrap, which ships `prefers-reduced-motion: reduce` blocks covering carousel, collapse/accordion, offcanvas, modal, spinners, and progress animation.
- IndigoKit adds no custom animation; respect the user's motion preference.

## Testing posture

- Every component task includes keyboard, focus, contrast, responsive, and (where applicable) live-region verification in the playground.
- Known environment limitation: automated accessibility tooling is not available in the build environment; evidence is browser-based DOM audits, interaction probes, and computed-style measurements.
