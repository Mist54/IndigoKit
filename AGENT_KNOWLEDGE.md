## 1. Overview

IndigoKit is a reusable **Modern + Enterprise UI framework on top of Bootstrap 5.3.x**.

- SCSS is the source styling language; the Sass CLI compiles it to CSS.
- Vanilla JavaScript (initial approach), Lucide icons.
- Preserve Bootstrap class names; extend Bootstrap components before creating new ones; new concepts get `mu-*` classes.
- No React, Angular, jQuery, Tailwind, TypeScript, or other UI frameworks without explicit approval.
- No new dependencies without approval (see rules: problem, why stack can't solve, why better than custom, bundle impact).

## 4. Build

```bash
npm run build:css   # SCSS → dist/css/indigokit.css
npm run build:js    # src/js/indigokit.js → dist/js/indigokit.js (plain copy)
```

`build:css` expands to:

```
sass --load-path=node_modules \
  --silence-deprecation=import \
  --silence-deprecation=global-builtin \
  --silence-deprecation=if-function \
  --silence-deprecation=color-functions \
  src/scss/indigokit.scss dist/css/indigokit.css
```

- Resolves `bootstrap` from `node_modules` via `--load-path`.
- Sass emits `dist/css/indigokit.css.map` by default — kept (useful for dev).
- Not minified (per rules, no strong reason yet).
- `build:js` is a standalone-file copy (`node -e` + `fs.mkdirSync/copyFileSync`, creates `dist/js/`). **No bundler, no modules, no new dependency.** `package.json` `type: "commonjs"` — the copied file is a plain IIFE, bundler-agnostic.

## 5. Conventions & process

- Bootstrap classes first, `mu-*` only for genuinely new concepts. No duplicate components.
- **Bootstrap public API preservation (permanent rule, see PROJECT_RULES.md §BOOTSTRAP PUBLIC API PRESERVATION):** for any component with an established Bootstrap class/API, keep the Bootstrap names and extend the implementation — never create a parallel `mu-*` class (`.mu-btn`, `.mu-card`, `.mu-table`, etc. are forbidden). `mu-*` only when Bootstrap has no equivalent concept or IndigoKit adds genuinely new functionality (`.mu-sidebar`, `.mu-app-navbar`, `.mu-app-content`).
- SCSS modular (base/components/layout/utilities/themes); avoid unnecessary overrides; no `!important` without documented reason; design tokens over hard-coded values.
- Every significant component needs a playground example (normal use, variants, responsive, dark mode, edge cases).
- **Styling architecture (permanent rule, see PROJECT_RULES.md §PLAYGROUND & STYLING ARCHITECTURE):** framework styling lives ONLY in `src/scss/` (compiled to `dist/css/indigokit.css`); the playground consumes the compiled output and never implements IndigoKit. Playground-only presentation styles go in `playground/playground.css`. Inline framework CSS in HTML (`<style>` or `style=""`) is **prohibited**; if a playground page needs behavior that should really be IndigoKit, move it into `src/scss/`.
- Build + check for SCSS errors + browser/responsive/a11y checks before calling a feature complete.
- **Incremental builds only** — small, understandable, testable, reusable pieces. Never generate the whole framework at once.
- On major architectural questions: pause and ask the human to obtain a decision (human mediates between FreeBuff and ChatGPT).

## 6. Design direction (Modern + Enterprise)

- Modern: clean, professional, whitespace, subtle shadows, controlled radius, modern type, restrained motion, light + dark themes.
- Enterprise: efficient screen space, excellent tables, strong forms, data-heavy UIs, filters/toolbars, clear nav, accessibility, responsive (desktop/tablet/mobile).
- Avoid: excessive gradients/animation, huge rounded cards, decorative UI, Dribbble-style flash.
